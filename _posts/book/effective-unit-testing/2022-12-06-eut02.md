# [2] 좋은 테스트란?

* toc 
{:toc}

좋은 테스트 고려사항  
- 테스트 코드의 가독성과 유지보수성
- 프로젝트 안에서, 그리고 소스 파일 안에서 코드는 적절히 구조화되어 있는가?
- 테스트가 무엇을 검사하는가?
- 테스트는 안정적이고 반복 가능한가?
- 테스트가 테스트 더블을 잘 활용하는가?


## 읽기 쉬운 코드가 유지보수도 쉽다

- 읽기 어려운 코드는 이해하는 데만 해도 너무 많은 에너지가 소비되기 때문에 유지보수하기 어려움
- 가독성과 결함 밀도는 반비례한다, 즉 읽기 어려운 코드일수록 결함 수가 많음
- 읽기 어려운 코드는 검증하기도 어렵고, 결과적으로 테스트를 조금만 작성하는 사태로까지 이어짐
- 제품의 구조와 api가 테스트를 고려하지 않고 만들어졌다면 결국 끔찍한 구조의 이해하기 어려운 테스트가 만들어짐

## 구조화가 잘 되어 있다면 이해하기 쉽다

- 구조화되어 있느냐 아니냐의 단순한 문제가 아니다. 쓸모있는 구조여야 함
- 코드가 도메인 모델이나 머릿속의 개념과 맞지 않아서 나눌 수 있는 명확한 경계를 찾을 수 없다면 차라리 나누지 않느니만 못할 수 있음
- 고수준 개념을 구현된 코드에 빠르고 정확하게 대입할 수 있는 구조면 됨
- 읽기 쉽고, 찾기 쉽고, 이해하기 쉽도록 한 가지 기능에 충실한 테스트 필요
    - 현재 작업과 관련된 테스트 클래스를 찾을 수 있음
    - 그 클래스에서 적절한 테스트 메서드를 고룰 수 있음
    - 그 메서드에서 사용하는 객체의 생명주기를 이해할 수 있음

## 엉뚱한 걸 검사하는 건 좋지 않다

- 테스트 이름은 검사 내용을 잘 나타낼 수 있어야 함
- 유지보수 관점에서는 어떻게 구현했느냐가 아니라 의도한 대로 구현했느냐를 검사하는 게 중요

## 독립적인 테스트는 혼자서도 잘 실행된다

- 테스트가 얼마나 독립적인가를 잘 살펴야 함
    - 아키텍처의 경계부분(다른 모듈이나 시스템을 사용하는 연결부)이 특히 중요
- 다음 요소와 관련이 있다면 각별한 주의 필요
    - 시간(Time)
    - 임의성(Randomness)
    - 동시성(Concurrency)
    - 인프라(Infrastructure)
    - 기존 데이터(Pre-exisitng Data)
    - 영속성(Persistency)
    - 네트워킹(Networking)
- 같은 테스트 클래스에 속한 테스트 메서드끼리도 순서를 가정하면 안 됨
    - 테스트를 서로 종속되지 않게 하라는 조언은 일반적으로 한 클래스의 테스트가 다른 클래스의 테스트 실행 여부나 그 결과에 의존하면 안 된다는 의미
    - 같은 클래스 내에서도 똑같음
- 실전에서 해 볼 수 있는 방법들
    - 테스트 더블로 서드파티(third party) 라이브러리와의 종속성 제거
        - 손수 만든 어댑터(adaptor)로 적절히 감싸줌
        - 성가신 부분이 어댑터 안으로 감춰져서 나머지 애플리케이션 로직과 분리해서 검사할 수 있음
    - 테스트에 필요한 자원을 테스트 코드와 같은 위치에 둠
    - 테스트가 사용할 자원을 직접 만듦
    - 테스트가 필요한 문맥을 직접 설정하게 함. 다른테스트에 의존 X
    - 영속성이 필요한 통합 테스트라면 인메모리(in-memory) 데이터베이스 활용
    - 스레드를 사용하는 코드는 동기식과 비동기식을 구분 지어서 골치 아픈 동시성 문제는 소규모의 전문 테스트 그룹에 맡김
        - 평범한 동기식 코드로 작성된 나머지 로직 대부분은 별다른 어려움 없이 검사할 수 있게 됨


## 믿음직한 테스트어야 기댈 수 있다
- 아무것도 검사하지 않는 테스트, 절대 실패하지 않는 테스트를 해선 안 됨
- 열 번 실행하면 열 번 모두 반드시 같은 결과가 나와야 함
- 애플리케이션이 비동기적 요소나 현재 시각에 종속된 코드를 포함한다면 그 부분을 인터페이스로 감싸 격리해야 함  
→ 텍스트 더블로 대체할 수 있어 반복 가능한 테스트를 만들 수 있음


## 모든 일이 그렇듯 테스트에도 도구가 쓰인다

자동화된 테스트 작성을 보조해주는 필수 도구 세 가지  
- 테스트 더블
    - 테스트를 위해 실제 구현체와 교체할 수 있는 객체
    - 프로그래머들이 흔히 스텁, 가짜 객체, Mock 객체 등으로 알고 있는 개념들을 통칭하는 용어
    - 원래의 로직을 간소화된 코드로 대체하여 테스트 속도를 개선
    - 만들어내기 어려운 특수한 상황을 시뮬레이션
    - 대상 객체의 내부 상태나 동작 등 테스트가 접근할 수 없던 정보를 얻어냄
- 테스트 프레임워크 (ex JUnit)
- 빌드 도구
    - 어떤 빌드 프로세스를 따르건, 어떤 도구와 기술을 이용한 빌드 스크립트를 만들건, 자동화된 테스트를 통합하지 않은 빌드는 용납될 수 없음
