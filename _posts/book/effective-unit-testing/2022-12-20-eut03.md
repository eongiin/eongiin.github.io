# [3] 테스트 더블

* toc 
{:toc}

테스트에서 아래와 같이 목적에 따라 비슷한 듯하면서도 다른 객체를 사용하는데 그 전부를 통틀어 <b>테스트 더블</b>이라 함
- 종속 모듈 없이 컴파일 하고 실행 가능
- 테스트 대상 코드 격리
- 속도 개선
- 예측 불가능한 요소 제어
- 특수한 상황 시뮬레이션
- 감춰진 정보를 얻어 냄

## 테스트 더블의 위력

### 테스트 대상 코드 격리

아래와 같이 두 가지로 분류
- 테스트 대상 코드
- 테스트 대상 코드와 상호작용하는 코드


```java
public class Car {

    private Engine engine;

    public Car(Engine engine) {
        this.engine = engine;
    }

    public void start() {
        engine.start();
    }

    public void drive(Route route) {
        for (Directions directions : route.directions()) {
            directions.follow();
        }
    }

    public void stop() {
        engine.stop();
    }
}
```

- 위 코드에서 Car를 테스트하려고 하면 직접 사용하는 Enigne, Route가 협력 객체고 이것들을 텍스트 더블로 교체해 주면 됨
- Directions는 Route를 거쳐서 얻어내므로, Route의 모조품을 직접 구현할 테니 그 안에 있는 Directions는 맘대로 만들 수 있음

### 테스트 속도 개선

- 테스트 더블로 협력 객체를 대체하면 원본을 그대로 사용할 때보다 빨라짐
- ex) Car가 이동할 최단 경로를 구할 때 Route가 가중 그래프 검색 알고리즘을 이용하는 경우
  - 모든 테스트가 매번 Route를 초기화하면 알고리즘 계산에만 수 초에서 수 분까지 허비될 수 있음
  - 테스트 더블을 이용해 사전에 계산해둔 경로를 반환하도록 하고, 경로 알고리즘은 별도의 테스트에서 따로 검증

### 예측 불가능한 실행 요소 제거
- ex) 경로 계산 알고리즘에 시간까지 고려하여 시간별로 다른 경로를 안내한다면?
  - 항상 똑같은 시간을 알려주는 테스트 더블로 시스템 시계를 갈아 끼워주면 훨씬 쉽게 예측 가능

### 특수한 상황 시뮬레이션
- 객체를 적절히 초기화해서 인자로 넣어줘도 거의 모든 상황 만들 수 있음
- ex) Route가 Directions를 구할 때 구글맵스를 이용하는 경우에 갑자기 인터넷이 끊겨 버리는 경우에 잘 대처하는지 테스트
  - 실행 도중에 테스트가 컴퓨터의 네트워크 인터페이스를 비활성화 시켜야 함  
  → 연결 요청을 처리하는 부분을 테스트 더블로 대체해서 예외를 발생시키면 됨

### 감춰진 정보 얻기
- 테스트가 얻을 수 없었던 정보에 접근 가능
- 테스트 대상 코드와 협력 객체 사이의 상호작용 확인
- ex) Car에 시동을 걸었을 때 Engine을 가동하는데, 이 동작이 실제로 일어났는지 확인하려는 경우
  - Car의 Engine을 테스트 더블로 교체하면 isRunning()과 같은 테스트 전용 메서드는 테스트 코드에만 추가하면 됨
    - 제품 코드는 건드리지 않음

```java
class CarTest {
    @Test
    @DisplayName("Car에 시동을 걸면 Engine이 가동된다")
    void engineIsStartedWhenCarStarts() {
        TestEngine engine = new TestEngine();
        new Car(engine).start();
        assertTrue(engine.isRunning));
    }

    public class TestEngine extends Engine {
        private boolean isRunning;

        public void start() {
            isRunning = true;
        }

        public boolean isRunning() {
            return isRunning;
        }
    }
}
```
 
## 테스트 더블의 종류

- 테스트 스텁
- 가짜 객체
- 테스트 스파이
- Mock 객체

### 테스트 스텁

- 테스트 스텁의 목적은 원래의 구현을 최대한 단순한 것으로 대체하는 것
- ex) 시스템 운영 정보를 로그 서버로 전송하는 코드
  - 로그 서버에 접근할 수 있는 유일한 통로는 Logger 인터페이스, 그 안에는 로그 생성 메서드가 하나 정의되어 있음

  ```java
  public class LoggerStub implements Logger {
      public void log(LogLevel level, String message) {}
  }
  ```
  - 아무일도 하지 않는 log 메서드
  - 만약 현재의 LogLevel를 반환하는 메서드도 정의되고 있다면 아래처럼 바뀌어야 함

  ```java
  public class LoggerStub implements Logger {
      public void log(LogLevel level, String message) {
      }

      public LogLevel getLogLevel() {
          return LogLevel.WARN; // 하드코딩된 값 반환
      }
  }
  ```

  - 무조건 LogLevel.WARN을 반환하도록 하드 코딩 되어있는데, 대부분의 경우에는 문제가 없음
    - 테스트는 대상 코드가 로깅하는 내용에는 전혀 관심이 없음
    - 가동 중인 로그 서버가 없으니 로깅은 어차피 실패함
    - 테스트 스위트가 콘솔로 대량의 정보를 쏟아내는건 바라지 않음 (파일에 쓰는 건 별로 상관없음)
  - 반환값을 하드코딩하는 테스트 스텁의 특성상 테스트 각자의 시나리오에 맞는 스텁을 따로 구현해야 함
  - 최소한의 행동을 취해주거나 입력값에 따라 다르게 행동했으면 할 때가 있다면 가짜 객체를 이용


### 가짜 객체
- 진짜 객체의 행동을 흉내 내지만, 진짜 객체를 사용할 때 생기는 부수 효과나 연쇄 동작이 일어나지 않도록 경량화하고 최적화한 것
- ex) 객체를 종류별로 저장하고 검색하는 저장소로 이루어진 영속 서비스
  - 그중 한 저장소의 API

  ```java
  public interface UserRepository {
    void save(User suer);
    User findById(long id);
    User findByUsername(String username);
  }
  ```

  - 테스트 더블을 사용하지 않는다면 이 저장소를 이용하는 코드를 검사하려는 모든 테스트는 어딘가에 있을 진짜 데이터베이스를 찾으려 할 것
  - 기본 타입만 다루는 간단한 인메모리 데이터베이스를 만들어 쓰기

  ```java
  import java.util.ArrayList;

  public class FakeUserRepository implements UserRepository {

      private Collectioin<User> users = new ArrayList<User>();

      @Override
      public void save(User suer) {
          if (findById(user.getId()) == null) {
              users.add(user);
          }
      }

      @Override
      public User findById(long id) {
          for (User user : users) {
              if (user.getId() == id) {
                  return user;
              }
          }
          return null;
      }

      @Override
      public User findByUsername(String username) {
          for (User user : users) {
              if (user.getUsername().equals(username)) {
                  return user;
              }
          }
          return null;
      }
  }
  ```

### 테스트 스파이
- 입력 인자로 사용되는 객체가 테스트에 필요한 정보를 알려주는 API를 제공하지 않을 때 유용
- ex)

  ```java
  public class DLog {
      private final DLogTarget[] targets;

      public DLog(DLogTarget... targets) {
          this.targets = targets;
      }

      public void write(Level level, String message) {
          for (DLogTarget each : targets) {
              each.write(level, message);
          }
      }

      public interface DLogTarget {
          void write(Level level, String message);
      }
  }
  ```

  - 테스트 대상인 DLog는 다수의 DLogTarget을 대표하는 분산 로그 객체
  - DLog에 메시지를 기록하면 그 안에 포함된 모든 DLogTarget에도 같은 내용 전달
  - DLogTarget에는 write() 메서드만 정의되어 있어 메시지가 잘 기록되었는지 알려주는 메서드가 존재하지 않음  
→ 테스트하기 골치 아픈 상황으로, 이때 테스트 스파이 사용

  ```java
  class DLogTest {
      @Test
      @DisplayName("DLog에 메시지를 기록하면 그 안에 포함된 모든 DLogTarget에도 전달된다")
      void writeEachMessageToAllTargets() {
          SpyTarget spy1 = new SpyTarget();
          SpyTarget spy2 = new SpyTarget();
          DLog log = new DLog(spy1, spy2);
          log.write(Level.INFO, "message");
          assertTrue(spy1.received(Level.INFO, "message"));
          assertTrue(spy2.received(Level.INFO, "message"));
      }

      private class SpyTarget implements DLog.DLogTarget {
          private List<String> log = new ArrayList<String>();

          @Override
          public void write(Level level, String message) {
              log.add(concatenated(level, message));
          }

          boolean received(Level level, String message) {
              return log.contains(concatenated(level, message));
          }

          private String concatenated(Level level, String message) {
              return level.getName() + ":" + message;
          }
      }
  }
  ```
  - 여느 테스트 더블과 똑같은 방식으로 진짜 객체 대체
  - 전달된 메시지 추적은 테스트 스파이가 맡음
  - 일을 마친 후 메시지가 잘 도착했는지 스파이로부터 확인
- 목격한 일을 기록해 두었다가 나중에 테스트가 확인할 수 있게끔 만들어진 테스트 더블
- 이 개념을 더 확장해서 완전한 Mock 객체로 발전시키기도 함

### Mock 객체
- 특수한 형태의 테스트 스파이
- 특정 조건이 발생하면 미리 약속된 행동을 취함
- 예상하지 않은 인자가 넘어왔거나, 아예 다른 메서드를 호출하면 테스트를 실패하게 만들 수 있고, 특정 메서드를 허용 횟수보다 많이 호출하거나 예상했던 연계 동작이 일어나지 않았을 때 실패하게 하는 것도 가능
- JMock, Mockito, EasyMock  등의 Mock 객체 라이브러리가 있음

## 테스트 더블 활용 지침

1. 용도에 맞는 더블 선택
  - 두 객체 간 상호작용의 결과로 특정 메서드가 호출되었는지 확인하고 싶다면 Mock 객체를 써야 할 가능성이 높음
  - Mock 객체를 사용하기로 했는데, 테스트 코드가 생각만큼 깔끔하게 정리되지 않는다면 더 단순한 테스트 스파이를 손수 작성해서도 똑같이 확인할 수 있는지 생각해 보기
  - 협력 객체는 자리만 지키면 되고 협력 객체가 대상 객체에 넘겨줄 응답도 테스트에서 통제할 수 있다면 스텁 사용  
  → 스텁을 쓰려고 했는데, 이미 Mock 객체도 사용 중이라면 스텁도 Mock 객체 라이브러리를 이용해서 생성  
  → 어차피 Mock 객체 라이브러리가 제공하는 기능이기도 하고, 테스트 코드도 읽기 편해짐
  - 필요한 서비스나 컴포넌트를 미처 준비하지 못해 스텁을 대용품으로 사용하고 있는데, 시나리오가 너무 복잡해서 벽에 부딪혔거나 테스트 코드가 관리하기 어려울 만큼 복잡해졌다면 가짜 객체를 구현하는 걸 고려해 보기
  - 스텁은 질문하고 Mock은 행동한다
2. 준비,시작,단언
- AAA (arrange-act-assert)
- 행위 주도 개발에도 GIVEN-WHEN-THEN 구조 존재
  - Given : 주어진 상황에서
  - When : 어떤 일이 발생했을 때
  - Then : 특정 결과 기대
3. 구현이 아닌 동작을 확인
- 테스트는 오직 한 가지만 검사해야 하고 그 의도를 명확히 전달하도록 작성되어야 함
- 검사하려는 동작은 무엇이고 굳이 확인할 필요 없는 부수적인 구현은 무엇인지 자문해 볼 필요 있음
- Mock에는 정말 바라고 의도한 핵심 동작만 설정하면 됨
- 부수적인 구현은 호출 횟수에 전혀 개의치 않는 관대한 Mock 객체나 스텁만으로도 충분
4. 자신의 도구를 선택
5. 종속 객체 주입
  - 진짜 객체를 다른 것과 교체할 방법이 없다면 테스트 더블도 무용지물
  - 종속 객체가 문제인데, 다른 객체로 교체해야만 쉽게 검사할 수 있다면 그 객체를 사용하는 곳과 생성하는 곳을 달리하는 것이 좋음  
  → 종속 객체를 private 필드에 저장하거나 팩토리 메서드 등을 통해 외부로부터 얻어야 함
  - 종속 객체를 떼어냈다면 `종속 객체 주입법`을 통해 종속 객체를 외부에서 안으로 집어넣음
    - 보통은 생성자 주입 방식 많이 이용
