4. 프로토콜 스택에 메시지 송신을 의뢰한다

- 브라우저는 URL을 해독하거나 HTTP 메시지를 만들지만, 메시지를 네트워크에 송출하는 기능은 없으므로 OS에 의뢰하여 액세스 대상의 웹 서버에 송신한다
- 이때 URL 안에 쓰여있는 서버의 도메인명에서 IP 주소를 조사해야 한다
    - OS에 송신을 의뢰할 때는 도메인명이 아니라 IP 주소로 메시지 받을 상대를 지정해야 하기 때문
- 이것을 알아보기 전에 간단히 IP 주소에 대해 정리해 보자

## 1. IP 주소의 기본

<b>TCP/IP 와 IP주소의 기본적인 개념</b>

- TCP/IP는 서브넷이라는 작은 네트워크를 라우터로 접속하여 전체 네트워크가 만들어짐
    - 여기서 서브넷이란 허브에 몇 대의 PC가 접속된 것
    - 이것을 한 개의 단위로 생각하여 '서브넷'이라고 부르는데, 라우터에서 연결하면 네트워크 전체 완성
- 여기에 네트워크 주소 할당
    - 00동 00번지라고 한다면
        - 동 - 서브넷 - 네트워크 번호
        - 번지 - 컴퓨터- 호스트 번호
    - 네트워크 번호 + 호스트 번호 → IP 주소
- IP 주소에 따라 액세스 대상이 어디 있는지 판단하고 운반
- 메시지를 보내면 서브넷 안에 있는 허브가 운반하고, 송신 측에서 가장 가까운 라우터까지 도착
- 라우터가 메시지 보낸 상대를 확인하여 다음 라우터 판단
- 거기에 보내도록 지시하여 송신 동작 실행 후 다시 서브넷의 허브가 라우터까지 메시지 보냄
- 이런 과정을 반복하여 도착

<b> IP 주소의 표기 방법</b>

- IP 주소 본체의 표기 방법
    - `12.34.56.78`
- IP 주소 본체와 같은 방법으로 네트워크 표기하는 방법
    - `12.34.56.78/255.255.255.0`
    - IP 주소 본체 + 넷마스크
- 네트워크 번호의 비트 수로 넷마스크를 표기하는 방법
    - `12.34.56.78/24`
- 서브넷을 나타내는 주소
    - `12.34.56.0/24`
    - 호스트 번호 부분의 비트가 모두 0인 것은 각 컴퓨터가 아니라 서브넷 자체를 나타냄
- 서브넷의 브로드캐스틀틀 나타내는 주소
    - `12.34.56.255/24`
    - 호스트 번호 부분의 비트가 모두 1인 것은 서브넷 전체에 대한 브로드캐스트를 나타냄

- 32비트를 8비트씩 점으로 구분하여 10진수로 표기
- 이것만으로는 어느 부분이 네트워크 번호인지 호스트 번호인지 알 수 없음
    - 두 가지를 합쳐서 32비트로 한다는 것만 결정되어 있음
    - 네트워크를 구축할 때 사용자가 직접 내역을 결정할 수 있음
    - 이 내역을 나타내는 정보를 필요에 따라 IP 주소에 덧붙임 → 넷마스크
- 넷마스크가 1인 부분은 네트워크 번호, 0인 부분은 호스트 번호를 나타냄
- 넷마스크로 네트워크 번호와 호스트 번호의 경계를 나타내는데, 경계가 바이트의 경계와 일치해도 되고 바이트의 도중에 경계를 두어도 상관없음

## 2. 도메인명과 IP 주소를 구분하여 사용하는 이유

- TCP/IP의 네트워크는 IP 주소로 통신 상대를 지정하므로 메시지를 송신하려면 IP 주소를 알아야 함
- 그렇다면 URL 안에 서버명이 아니라 IP 주소를 써도 되지 않는가
    - 써도 됨. 그러나 기억하기 어려움
- 그렇다면 IP 주소 말고 이름으로 상대를 지정하여 통신하는 것은?
    - 실행 효율이라는 관점에서 좋은 방법이라 할 수 없음
    - IP 주소는 32비트, 즉 4바이트에 해당하는 개수밖에 없지만, 도메인명은 적어도 수십 바이트부터 최대 255바이트나 있음
    - IP 주소라면 4바이트 분의 수치만 취급하면 되지만, 도메인명이라면 수십 바이트에서 255바이트까지의 문자를 취급해야 함
    - 길뿐만 아니라 길이가 결정되어 있지도 않아 더 복잡함
    - 그만큼 라우터가 부하되어 데이터를 운반하는 동작에 더 많은 시간이 걸리며 네트워크 속도가 느려짐
        - 고성능 라우터를 사용하면? 한계가 있으며 한계에 다다르면 방대한 양의 데이터가 인터넷의 내부에 정체되어 있을 수 있음
- 사람은 이름을 사용하고, 라우터는 IP 주소를 사용하자 → DNS


## 3. Socket 라이브러리가 IP 주소를 찾는 기능을 제공한다

- IP 주소를 조사하려면 DNS 서버에서 조회
- DNS 서버로 조회 메시지를 보내고 응답 메시지를 받아야 함
    - 이것은 DNS 서버에 대해 클라이언트로 동작한다고 말할 수 있음
    - DNS 클라이언트에 해당하는 것을 DNS 리졸버 또는 단순히 리졸버라고 부름
- DNS의 원리를 사용하여  IP 주소를 조사하는 것을 네임 리졸루션(name resolution)이라고 하는데 이 리졸루션을 실행하는 것이 리졸버
- 리졸버의 실체는 Socket 라이브러리에 들어있는 부품화한 프로그램
- Socket 라이브러리
    - 라이브러리는 다양한 애플리케이션에서 이용할 수 있도록 부품화한 여러 개의 프로그램을 모아놓은 것, 프로그램의 부품집
    - Socket 라이브러리는 이러한 라이브러리의 일종으로 OS에 포함되어 있는 네트워크 기능을 애플리케이션에서 호출하기 위한 부품을 모아놓은 것
    - 리졸버는 그 속에 들어있는 프로그램 부품의 하나

## 4. 리졸버를 이용하여 DNS 서버를 조회한다
- 애플리케이션 프로그램을 만들 때 리졸버의 프로그램명(gethostbyname)과 웹 서버의 이름(www.abcd.co.kr)을 쓰기만 하면 리졸버를 호출할 수 있음
    - `<메모리 영역> gethostbyname("www.abcd.co.kr");`
    - 메모리 영역 안에 서버의 IP 주소가 기입됨
- 이렇게 리졸버를 호출하여 DNS 서버에 조회 메시지를 보내고, DNS 서버에서 응답 메시지가 돌아옴
- 응답 메시지 속에 IP 주소가 포함되어 있어 리졸버가 이것을 추출하여 브라우저에서 지정한 메모리 영역에 넣음
- 브라우저가 웹 서버에 메시지를 보낼 때는 이 메모리 영역에서 IP 주소를 추출하여 HTTP의 리퀘스트 메시지와 함께 OS에 건네주어 송신 의뢰할 뿐

## 5. 리졸버 내부의 작동
- 네트워크 애플리케이션이 리졸버를 호출하면 제어가 리졸버의 내부로 넘어감
- 리졸버에서는 DNS 서버에 문의하기 위한 메시지를 만듦
    - 브라우저가 웹 서버에 보내는 HTTP의 리퀘스트 메시지를 만드는 것과 유사
    - '`www.abcd.co.kr`이라는 서버의 IP 주소를 가르쳐 주세요'
- 이 메시지를 DNS 서버에 보내는데 메시지 송신 동작은 리졸버가 스스로 실행하는 것이 아닌 OS 내부에 포함된 프로토콜 스택을 호출하여 실행 의뢰
    - 프로토콜 스택 : OS 내부에 내장된 네트워크 제어용 소프트웨어로, '프로토콜 드라이버', 'TCP/IP 소프트웨어' 등으로도 부름
    - 리졸버도 브라우저와 같이 네트워크에 대해 데이터를 송·수신하는 기능이 없기 때문
- 리졸버가 프로토콜 스택을 호출하면 제어가 이곳으로 넘어가고, 여기에서 메시지 보내는 동작을 실행하여 LAN 어댑터를 통해 메시지가 DNS 서버를 향해 송신됨
- 조회 메시지가 조사하는 방법은 뒤에서 다룸
- 액세스 대상의 웹 서버가 DNS 서버에 등록되어 있으면 답이 발견되므로 답을 응답 메시지에 써서 클라이언트에게 반송함
- 네트워크를 통해 클라이언트 측에 도착하고, 프로토콜 스택을 경유하여 리졸버에게 건네져서 리졸버가 내용을 해독한 후 여기에서 IP 주소를 추출하여 애플리케이션에 IP 주소 건네줌 (리졸버를 호출할 때 지정한 메모리 영역에 IP 주소 저장)
- DNS 서버에 메시지를 송신할 때도 DNS 서버의 IP 주소가 필요하지만, 이것은 TCP/IP 설정 항목의 하나하나로 컴퓨터에 미리 설정되어 있음
