## 1. 탐험은 URL 입력부터 시작

**URL (Uniform Resource Locator**  
- http:~, file:~, mailto:~ 등 여러 종류의 URL이 있다
    - 브라우저는 몇 개의 클라이언트 기능을 겸비한 복합적인 클라이언트 소프트웨어라고 할 수 있음
    - 여러 기능 중 어느 것을 사용하여 데이터에 액세스하면 좋은지 판단하기 위해 여러 종류의 URL이 있는 것
    - `http://~` : HTTP 프로토콜로 웹 서버에 액세스하는 경우
    - `ftp://~` : FTP 프로토콜로 파일을 다운로드하거나 업로드하는 경우
    - `file://~` : 클라이언트 PC 자체의 파일에서 데이터를 읽어오는 경우 
    - `mailto:~` : 메일을 송신하는 경우
    - `news:~` : 뉴스그룹의 기사를 읽는 경우
    - URL의 맨 앞부분에는 액세스 방법이 나와있음
      - `file:`과 같이 네트워크를 사용하지 않는 것도 있으므로 프로토콜을 나타낸다고 단언할 수는 없음
    
## 2. 브라우저는 먼저 URL을 해독한다

- 브라우저가 처음 하는 일은 웹 서버에 보내는 리퀘스트의 메시지를 작성하기 위해 URL을 해독하는 것

ex) 웹 서버에 액세스하는 경우  
- `http://웹서버명/디렉토리명/…/파일명`
  - `http:` : 데이터 출처에 액세스하는 방법, 즉 프로토콜
  - `//` : 나중에 이어지는 문자열이 서버의 이름임을 나타냄
  - `/디렉토리/~/파일명` : 데이터 출처(파일)의 경로명을 나타냄, 생략 가능

## 3. 파일명을 생략한 경우

- `http://웹서버명/디렉토리명/`
  - 끝이 `/`로 끝난 것은 디렉토리명 다음에 써야 할 파일명을 쓰지 않고 생략한다는 것
  - 파일명 생략 가능, 대신 생략하면 어느 파일에 액세스해야 할지 몰라서 이 경우를 대비해 서버 측에 미리 설정해 둠
    - 대부분 `index.html` or `default.html`
- `http://웹서버명/`
  - `/`라는 디렉토리(루트 디렉토리)가 지정되고 파일명은 생략된 것
- `http://웹서버명`
  - 디렉토리명까지 생략한 경우
  - 지나친 생략일 수 있으나 가능함
  - 루트 디렉토리 아래에 있는 미리 설정된 파일명의 파일(ex `/index.html`) 에 액세스 함
- `http://웹서버명/abcd`
  - 맨 끝에 `/`가 없으므로 abcd를 파일명으로 보는 것이 맞는 느낌
  - 하지만 실제로는 디렉토리의 끝에 있는 `/`까지 생략해 버리는 경우가 있음
  - 보통 이 경우에는 웹 서버에 abcd라는 파일이 있으면  abcd를 파일명으로 보고, abcd라는 디렉토리가 있으면 디렉토리명으로 봄
    - 같은 경로에 같은 이름을 가진 파일과 디렉토리를 둘 다 만들 수 없으니까

## 4.  HTTP의 기본 개념

- 클라이언트와 서버가 주고받는 메시지의 내용이나 순서를 정한 것
- 먼저 클라이언트에서 서버를 향해 '무엇을', '어떻게 해서' 하겠다는 내용의 리퀘스트 메시지를 보냄
  - 무엇을 : URI(Uniform Resource Identifier)  
    - 보통 페이지 데이터를 저장한 파일의 이름이나 CGI 프로그램의 파일명을 URI로 씀(URI에 URL 포함)
  - 어떻게 해서 : 메소드  
    - 메소드에 의해 웹 서버에 어떤 동작을 하고 싶은지 전달
    - ex) GET, POST …
  - 보충 정보를 나타내는 헤더 파일도 있음
- 웹 서버는 받은 리퀘스트 메시지를 해독하고 URI와 메시지를 조사하여 '무엇을', '어떻게 하는지' 판단 후 요구에 따라 동작하고, 결과 데이터를 응답 메시지에 저장
  - 응답 메시지 맨 앞에는 실행 결과가 정상 종료되었는지 확인할 수 있는 스테이터스 코드 존재
    - EX) `404 Not Found`
- 그 뒤로 헤더 파일, 페이지의 데이터가 담긴 응답 메시지를 클라이언트에 반송
- 클라이언트에 응답메시지가 도착하여 브라우저가 메시지의 안에서 데이터를 추출하여 화면에 표시하면 HTTP 동작 끝

## 5. HTTP 리퀘스트 메시지를 만든다
- 브라우저는 URL을 해독하고 웹 서버와 파일명을 판단하면 이것을 바탕으로 HTTP의 리퀘스트 메시지를 만듦
- 리퀘스트 메시지는 리퀘스트 라인, 메시지 헤더, 메시지 본문으로 구성
  - 리퀘스트 라인
    - 리퀘스트의 내용을 대략 알 수 있음
    - `<메소드><공백><URI><공백><HTTP버전>`
  - 메시지 헤더
    - 한 행에 한 개의 헤더 필드를 씀
    - 리퀘스트의 부가적인 정보 나타냄
      - 날짜, 클라이언트 측이 취급하는 데이터의 종류, 언어, 압축 형식, 클라이언트나 서버의 소프트웨어 명칭과 버전, 데이터의 유효 기간이나 최종 변경 일시 등
    - [표준 헤더](https://en.wikipedia.org/wiki/List_of_HTTP_header_fields){:target="_blank"}
    - 필요시 임의의 헤더 추가 가능
    - 행 수는 상황에 따라 달라지며 마지막 공백 행까지 메시지 헤더
    - `<필드명>:<필드값>`
  - 메시지 본문
    - 클라이언트에서 서버에 송신하는 데이터

  ```
  GET /search?q=eongiin&hl=ko HTTP/1.1
  Host: www.google.com
  .
  .


  ```
- 응답 메시지는 스테이터스 라인, 메시지 헤더, 메시지 본문으로 구성
  - 스테이터스 라인
    - 스테이터스 코드의 내용을 나타내는 짧은 설명문
    - `<HTTP 버전><공백><스테이터스 코드><공백><응답 문구>`
  - 메시지 헤더
  - 메시지 본문
    - 서버에서 클라이언트에 송신하는 데이터
    - 메시지 본문은 바이너리 데이터로 취급
  
  ```
  HTTP/1.1 200 OK
  Content-Type:text/html;charset=UTF-8
  Content-Length:1004

  <html>
    <body>...</body>
  </html>
  ```

## 6. 리퀘스트 메시지를 보내면 응답이 되돌아온다

- 정상 종료했는지, 오류가 발생했는지 리퀘스트의 실행 결과를 나타내는 스테이터스 코드와 응답 문구를 첫 번째 행에 써야 함
  - 스테이터스 코드 : 숫자, 주로 프로그램 등에 실행 결과를 알려주는 것이 목적
    - 1xx (Informational) : 요청이 수신되어 처리 중
    - 2xx (Successful) : 요청 정상 처리
    - 3xx (Redirection) : 요청을 완료하려면 추가 행동이 필요
    - 4xx (Client Error) : 클라이언트 오류, 잘못된 문법 등으로 서버가 요청을 수행할 수 없음
    - 5xx (Server Error) : 서버 오류, 서버가 정상 요청을 처리하지 못함
  - 응답 문구 : 문장, 사람에게 실행 결과를 알리는 것이 목적
- 응답 메시지가 되돌아오면 그때부터 데이터를 추출한 후 화면에 표시
  - 페이지가 문장으로만 되어 있으면 이것으로 끝이지만 영상 등이 포함되어 있으면 다시 한번 웹 서버에 액세스하여 관련 태그에 쓰여있는 영상 파일을 웹 서버에서 읽어와 표시
  - 리퀘스트 메시지에 쓰는 URI는 한 개만으로 결정되어 있으므로 파일을 한 번에 한 개씩만 읽을 수 있어 따로따로 읽어야 함
  - 웹 서버에서는 이러한 사정을 전혀 신경 쓰지 않고 단순히 한 개의 리퀘스트에 대해 한 개의 응답만 돌려보낼 뿐
