### Servlet
- HttpServlet 상속
  - protected void service 오버라이드
  - `@WebServlet(name = "서블릿 이름", urlPattern = "/abc/de")`
- 서블릿 컨테이너 동작 방식 (스프링 부트 이용)
  - 스프링 부트 실행하면 내장 톰캣 서버 띄움
  - 톰캣 서버는 내부에 서블릿 컨테이너 기능을 가지고 있어서 이를 이용해 서블릿 생성
- HttpServletRequest
  - 서블릿이 HTTP 요청 메시지를 파싱 하여 그 결과를 객체로 담아서 제공해 줌
- HTTP 요청 메시지를 통해 클라이언트에서 서버로 데이터를 전달하는 방법
  - GET - 쿼리 파라미터
    - /url<b>?name=eongiin&age=20</b>
    - 메시지 바디 없이, URL의 쿼리 파라미터에 데이터를 포함해서 전달
    - ex) 검색, 필터, 페이징 등
    - `request.getParameter(name)`
  - POST - HTML Form
    - `content-type:application/x-www-form-urlencoded`
    - 메시지 바디에 쿼리 파라미터 형식으로 전달 `name=eongiin&age=20`
    - ex) 회원 가입, 상품 주문, HTML Form
    - 웹 브라우저가 HTTP 메시지 만들어 줌
    - `request.getParameter(name)`
      - 서버 입장에서는 GET URL 쿼리 파라미터 형식과 POST HTML Form 형식이 동일해서 `request.getParameter()`로 구분 없이 조회 가능
  - HTTP message body에 데이터 직접 담아서 요청
    - HTTP API에서 주로 사용, JSON, XML, TEXT
    - 데이터 형식은 주로 JSON 사용
    - POST, PUT, PATCH
    - 단순 텍스트 
    - JSON
      - 메시지 바디의 내용을 바이트 코드로 얻기
        - `ServletInputStream inputStream = request.getInputStream()`
      - 스트링으로 변환
        - `String messageBody = StreamUtils.copyToString(inputStream, StandardCharsets.UTF_8)`
      - 객체로 변환
        - `objectMapper.readValue(messageBody, 객체명.class)`
- HttpServletResponse
  - `response.setContentType("text/plain");`
  - `response.setCharacterEncoding("utf-8");`
  - `response.sendRedirect("/hello.html");`

### JPA를 사용해야 하는 이유
- SQL 중심적인 개발에서 객체 중심으로 개발
- 생산성
  - `jpa.persist(member)`
  - `jpa.find(memberId)`
  - `member.setName("수정")`
  - `jpa.remove(member)`
- 유지보수
  - 필드 변경시 그냥 추가하기만 하면 됨
  - SQL은 JPA가 처리
- 패러다임의 불일치 해결
  - 상속
    - 저장 : persist()에 자식만 넣으면 부모와 자식 모두 쿼리 날려줌
    - 조회 : 상속 관계의 entity에 대해 알아서 join
  - 연관관계, 객체 그래프 탐색
    - 자바 컬렉션에 넣었던 것처럼 Member만 조회해도 연관 관계가 있는 Team도 함께 조회 가능
  - 비교
    - 같은 트랙잭션 안에서 조회한 entity는 같음을 보장
- 성능
  - 시스템에 중간 계층이 있으면 캐시 등을 이용해 성능을 높일 수 있는데, JPA가 이 중간 계층에 해당
  - 복잡한 로직으로 인해 같은 테이블 계속 조회하는 일이 생긴다면 처음 조회한 것은 SQL로 가져오지만 같은 PK 값으로 다시 조회하면 캐시에서 가져옴
  - 한 트랜잭션 안에서만 보장되는 짧은 캐시라 실무에서 성능적으로 크게 도움 되진 않지만 알아는 두기
- 데이터 접근 추상화와 벤더 독립성
- 표준
### JPA 설정
- 라이브러리 추가 (JPA 하이버네이트, DB)
- `/META-INF/persistence.xml`
  - `persistence-unit name` 이름 지정
  - `javax.persistence ~`: JPA 표준 속성
    - `javax.persistence.jdbc.driver`
    - `javax.persistence.jdbc.user`
    - `javax.persistence.jdbc.password`
    - `javax.persistence.jdbc.url`
  - `hibernate ~` : 하이버네이트 전용 속성
    - `hibernate.dialect`
- EntityManagerFactory
  - 애플리케이션 실행 시점에 하나만 생성하여 애플리케이션 전체에 걸쳐 공유
- EntityManager
  - 요청이 왔을 때 썼다가 끝나면 버리는 사이클 반복
  - 절대 스레드 간 공유 X 사용하고 바로 버리기
- JPA의 모든 데이터 변경은 트랜잭션 안에서 실행해야 함

### JPQL
- JPA가 제공하는 SQL을 추상화한 객체 지향 쿼리 언어
- 특정 데이터베이스에 의존하지 않음
- SQL과 문법 유사
- 필요한 이유
  - JPA를 사용하면 Entity 객체를 중심으로 개발하게 되는데, 검색 또한 테이블이 아닌 Entity 객체를 대상으로 함
  - 모든 DB 데이터를 객체로 변환해서 검색하는 것은 불가능
  - 필요한 데이터만 DB에서 불러오려면 검색 조건이 포함된 SQL 필요
    - 하지만 쿼리를 쓰면 SQL에 종속됨
    - 이때 객체를 대상으로 검색할 수 있게 하는 기술이 JPQL
- 나중에 더 자세히 공부할 예정

### 영속성 관리
- 영속성 컨텍스트
  - Entity를 영구 저장하는 환경
    - `em.persist(member)` : 영속 컨텍스트에 member 객체 저장
  - EntityManager를 통해 접근
    - J2EE, 스프링 프레임워크 같은 컨테이너 환경에서는 엔티티 매니저와 영속성 컨텍스트가 N:1
  - 이점
    - 1차 캐시
    - 동일성 보장
      - 1차 캐시로 반복 가능한 읽기(repeatable read) 등급의 트랜잭션 격리 수준을 데이터베이스가 아닌 애플리케이션 차원에서 제공
    - 트랜잭션을 지원하는 쓰기 지연(transactinal write-behind)
      - 메모리에 쿼리를 쌓고 있다가 커밋 하는 순간 데이터베이스에 INSERT SQL 보냄
      - `<property name="hibernate.jdbc.batch_size" value="10"/>`
        - value 값 만큼 쿼리를 모아서 한꺼번에 DB에 날릴 수 있는 옵션
      - persist() 할 때마다 DB에 쿼리를 날리면 최적화하기 어려움
      - 이렇게 여러 개를 한 번에 모아서 보내면, 옵션 하나로 성능 최적화 가능
    - 변경 감지(dirty checking)
      - 1차 캐시에는 키(id)와 값(entity) 외에도 스냅샷이 있음
        - 스냅샷 - 최초로 영속성 컨텍스트에 들어온 상태를 본 떠둔 것
      - 커밋하는 시점에 내부적으로 flush() 하면서 Entity와 스냅샷 비교
        - 일일이 비교해서 바뀐게 있으면 update 쿼리 생성하여 쓰기 지연 SQL 저장소에 저장후 DB에 반영
      - 이러한 이유로 수정한 후 따로 persist()를 호출하지 않아도 됨
    - 지연 로딩(lazy loading)
- 엔티티의 생명주기
  - 비영속 (new/transient)
    - 영속성 컨텍스트와 전혀 관계가 없는 새로운 상태
  - 영속 (managed)
    - 영속성 컨텍스트에 관리되는 상태
  - 준영속 (detached)
    - 영속성 컨텍스트에 저장되었다가 분리된 상태
  - 삭제 (removed)
    - 삭제된 상태
- 플러시
  - 영속성 컨텍스트의 변경 내용을 데이터베이스에 반영
    - 영속성 컨텍스트를 비우는 개념이 아님
  - 영속성 컨텍스트를 플러시 하는 방법
    - em.flush()
    - 자동 호출
      - 트랜잭션 커밋
      - JPQL 쿼리 실행
        - 아직 커밋하지 않은 persist 대상에 JPQL 쿼리를 날릴 경우 해당 데이터를 불러올 수 없으니까

### Entity 매핑
- `@Entity`
  - JPA가 관리하는 객체
  - JPA를 사용해서 테이블과 매핑할 클래스는 `@Entity` 필수
  - 기본 생성자 필수로 구현
    - 파라미터가 없는 public 또는 protected 생성자
  - final 클래스, enum, interface, inner 클래스 사용 x
  - 저장할 필드에 final 사용 x
- DDL 생성 기능
  - 제약 조건 추가
    - `@Column(nullable = false, length = 20)`
  - 유니크 제약 조건 추가
    - `@Table(uniqueConstraints = {@UniqueConstraint( name = "NAME_AGE_UNIQUE", columnNames = {"NAME", "AGE"} )})`
  - DDL 생성 기능은 DDL을 자동 생성할 때만 사용되고 JPA 실행 로직에는 영향 X
- 매핑 어노테이션 정리
  - `@Column` 컬럼 매핑
    
    |속성|설명|기본값|
    |:--:|:--:|:--:|
    |name|필드와 매핑할 테이블의 컬럼 이름|객체의 필드 이름|
    |insertable,updatable|등록, 변경 가능 여부|TRUE|
    |nullable(DDL)|null 값 허용 여부 설정<br/> false로 설정하면 DDL 생성 시 not null 제약 조건 붙음||
    |unique(DDL)|@Table의 uniqueConstraints와 같음<br/> unique 키가 랜덤 이름으로 나와 알아보기가 힘들어 잘 안 쓰고 위와 같이 씀||
    |columnDefinition(DDL)|데이터베이스 컬럼 정보를 직접 줄 수 있음<br/> ex) `varchar(100) default 'EMPTY`||
    |length(DDL)|문자 길이 제약조건. String 타입에만 사용|255|
    |precision, scale(DDL)|BigDecimal 타입에서 사용(BigInteger도 사용 가능)<br/> precision은 소수점을 포함한 전체 자릿수<br/> double, float 타입에는 적용 x<br/> 아주 큰 숫자나 정밀한 소수를 다루어야 할 때만 사용|precision = 19<br/> scale = 2|
    
  - `@Temporal` 날짜 타입 매핑
    - 날짜 타입(java.util.Date, java.util.Calendar) 매핑할 때 사용
    - LocalDate, LocalDateTime을 사용할 때는 생략 가능(최신 하이버네이트 지원)
  - `@Enumerated` enum 타입 매핑
    - EnumType.ORDINAL (기본값): enum 순서를 데이터 베이스에 저장
      - 사용하지 말 것!
    - EnumType.STRING : enum 이름을 데이터 베이스에 저장
  - `@Lob` BLOB, CLOB 매핑
    - 매핑하는 필드 타입이 문자면 CLOB 매핑, 나머지는 BLOB 매핑
      - CLOB : String, char[], java.sql.CLOB
      - BLOB : byte[], java.sql.BLOB
  - `@Transient` 특정 필드를 컬럼에 매핑하지 않음(매핑 무시)
    - 데이터베이스에 저장 X, 조회 X
    - 주로 메모리상에서만 임시로 어떤 값을 보관하고 싶을 때 사용
- 기본 키 매핑
  - 직접 할당 : @Id만 사용
  - 자동 생성(@GeneratedValue)
    - IDENTITY: 데이터베이스에 위임, MYSQL 
      - 이 경우 ID 값은 DB에 insert 쿼리로 데이터가 실제로 들어가야 알 수 있음
      - 그런데 영속성 컨텍스트에서 관리되려면 PK 값이 필요
        - 그래서 em.persist() 호출하자마자 바로 insert 쿼리 날림
    - SEQUENCE: 데이터베이스 시퀀스 오브젝트 사용, ORACLE 
      - @SequenceGenerator 필요
    - TABLE: 키 생성용 테이블 사용, 모든 DB에서 사용
      - @TableGenerator 필요
    - AUTO: 방언에 따라 자동 지정, 기본값

## ✏️ Spring MVC
[스프링 MVC 1](https://www.inflearn.com/course/%EC%8A%A4%ED%94%84%EB%A7%81-mvc-1/dashboard){:target="_blank"}

```java
public class MemberRepository {
    private static Map<Long, Member> store = new HashMap<>(); //static 사용
    private static long sequence = 0L; //static 사용
    private static final MemberRepository instance = new MemberRepository();

    public static MemberRepository getInstance() {
        return instance;
    }

    private MemberRepository() {
    }

    public Member save(Member member) {
        member.setId(++sequence);
        store.put(member.getId(), member);
        return member;
    }

    public Member findById(Long id) {
        return store.get(id);
    }

    public List<Member> findAll() {
        return new ArrayList<>(store.values());
    }

    public void clearStore() {
        store.clear();
    }
}
```

- 동시성 문제가 고려되어 있지 않음, 실무에서는 ConcurrentHashMap, AtomicLong 사용 고려
- 싱글톤 패턴 적용
  - 스프링 빈으로 등록하면 자동으로 싱글톤을 보장해 주지만 최대한 순수 서블릿 만으로 구현해 봄
  - 생성자 private로 막기
  - getInstance()로 얻기
- store, sequence는 하나만 만들어져야 해서 static 붙임
  - 위 예제에선 싱글톤 패턴을 적용해서 안 해도 되긴 하지만 일단 붙여둠

  - forward
    - 서버 내부에서 일어나는 호출
    - 클라이언트는 인지하지 못함

## ✏️ JPA

### 연관관계 매핑 기초

- 객체를 테이블에 맞추어 모델링 하면, 협력 관계를 만들 수 없음
  - 테이블은 외래 키로 조인을 사용해서 연관될 테이블 찾음
  - 객체는 참조를 사용해서 연관된 객체를 찾음
  - 테이블과 객체는 큰 간격이 있어 테이블 중심 모델링을 하면 식별자로 다시 조회해야 하고, 이는 객체 지향적인 방법이 아님
  - 객체 지향 모델링 필요
- 양방향 연관관계
  - 테이블은 변화가 없다. 조인해서 양쪽 다 볼 수 있음. 방향이라는 개념이 없음
  - 객체에서는 양쪽에 다 넣어줘야 함
    - 사실상 서로 다른 단방향 연관관계가 두 개 있는 것
  - 양방향 매핑 규칙
    - 객체의 두 관계 중 하나를 연관관계의 주인으로 지정
    - <b>연관관계의 주인만이 외래 키를 관리(등록, 수정)</b>
    - <b>주인이 아닌 쪽은 읽기만 가능</b>
    - 주인은 mappedBy 속성 사용 x
    - 주인이 아니면 mappedBy 속성으로 주인 지정
  - 외래 키가 있는 곳을 주인으로 정하기 (N 쪽)
  - 멤버(N)와 팀(1)을 양방향 매핑 시킨다면
    - Member

    ```java
    @ManyToOne
    @JoinColumn(name = "TEAM_ID")
    private Team team
    ```
  
    - Team

    ```java
    @OneToMany(mappedBy = "team")
    List<Member> members = new ArrayList<Member>();
    ```

  - 양방향 매핑 시 주의점
    - 연관관계의 주인에 값을 꼭 입력해야 함  
    - 순수한 객체 관계를 고려하면 항상 양쪽 다 값을 입력해야 함
      - 연관관계 편의 메소드 생성하면 좋음
        - 이름을 꼭 setTeam으로 할 필요 없고 changeTeam 등으로 바꾸면 일반 setter가 아닌 것을 알아보기 쉬워서 더 좋음
        - 둘 중 한 곳에서만 만들고 양쪽 값을 다 넣기만 하면 됨

      ```java
      public void setTeam(Team team){
        this.team=team;
        team.getMembers().add(this);
      }
      ```

      - 양쪽 모두 값을 입력하지 않았을 때 생길 수 있는 문제 상황
        - Team을 먼저 불러와 Team이 영속 컨텍스트에 저장되어 있는 상태에서 주인(Member)에만 값을 넣고(Team) Team에는 Member 정보를 넣지 않았을 때 Team의 식별자로 해당 Team 정보를 불러오면 쿼리를 날리지 않고 1차 캐시에서 가져오기 때문에 Team 쪽에는 아직 Member 정보가 없어서 Member 값에 접근 못함
        - 테스트 케이스 작성할 때 JPA 없이도 작동할 수 있게 해야 하는데 이때도 이상하게 나올 수 있음
    - 무한 루프 주의
      - ex) toString(), lombok, JSON 생성 라이브러리
        - controller에는 Entity를 반환하지 말 것 → DTO로 변환해서 반환하기
          - 무한 루프 생길 수 있음
          - Entity를 변경하는 순간 API 스펙이 바뀜
  - 양방향 매핑 정리
    - 단방향 매핑만으로도 이미 연관관계 매핑은 완료
    - 양방향 매핑은 반대 방향으로 조회(객체 그래프 탐색) 기능이 추가된 것뿐
    - JPQL에서 역방향으로 탐색할 일이 많음
    - 단방향 매핑을 잘 하고 양방향은 필요할 때 추가해도 됨(테이블에 영향을 주지 않음)
